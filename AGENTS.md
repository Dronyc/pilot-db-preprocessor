# AGENTS.md — инструкции для агентов проекта pilot-db-preprocessor

Этот файл читают браузерные агенты (QWEN-Coder, ревьюер QWEN, исполнительные чаты)
и локальные кодеры. Он задаёт постоянные правила. Текст задачи приходит отдельно
(форма B из docs/Handoff.md) и не дублирует этот файл.

## 1. Роль и границы

- QWEN-Coder пишет код в файлах `*.bas`. Автор правок в `*.bas` — только он.
- Ревьюер QWEN читает PR и выносит вердикт. Правок не вносит.
- DeepSeek формирует текст задачи. Код не пишет.
- Владелец ставит глобальные задачи, тестирует книгу Excel, вносит мелкие правки
  через VS Code, создаёт PR и сообщает SHA (зона пользователя).
- Препроцессор не вызывает внешний ИИ, не правит исходные файлы, не удаляет
  папки и файлы, не делает push в GitHub.

## 2. Ветки и PR

- `main` защищена. Прямой push запрещён.
- Рабочая ветка кодера — `for-coder`. PR — `for-coder`
  (релизы `for-coder` → `main` — отдельным PR по вехам).
- Имя рабочей ветки: `for-coder/W<N>-<краткое-описание-латиницей>`.
- Имя PR: `[W<N>] <краткое описание на русском>`.
- В описании PR указать: ID задачи (`OPT-xx`), код задачи (`W<N>`),
  краткий список изменений, список выполненных проверок.
- Шаблон PR — `.github/PULL_REQUEST_TEMPLATE.md`. Если он сбивает кодера —
  шаблон можно временно удалить, код при этом не страдает.
- PR и SHA — зона пользователя. Кодер PR не создаёт, SHA в чат не сообщает.

## 3. Definition of Done (обязательно в том же PR)

1. `docs/Spec_Optimization.md` — колонка «Статус»: `<ID>` → «Выполнено».
2. `docs/Journal.md` — запись по шаблону журнала: дата, `<ID>`, что сделано
   (1–3 строки), SHA — прочерк «не заполняется» (трассируемость — по дате, ID и метке коммита).
3. `docs/Project_Map.md` — обновить, если менялась архитектура/состав модулей/
   карта промтов; иначе строкой «Project_Map.md не менялся: архитектура без
   изменений».
4. `prompts/CHANGELOG.md` — запись, если менялись `prompts/*.md`; иначе строкой
   «CHANGELOG не менялся: промты не затрагивались».
5. В описании PR — изменённые файлы и критерии приёмки, по одному пункту
   на критерий.
6. Сообщить в чат: «<ID> готов к PR».

Правило: если хотя бы один из пп. 1–4 не выполнен — PR не принимается
(возврат на доработку), даже если код корректен.

## 4. Ограничения по коду

- Трогать только файлы, перечисленные в задаче. Чужие модули не затрагивать.
- Журналирование — только через `Mod_Util`: `WriteLog` (`[i] <текст>`),
  `WriteError` (`ERROR [<код>]: <текст>`), `WriteWarning` (`[!] <текст>`).
  Прямые записи в лог в обход `Mod_Util` запрещены.
- Новые ошибки/предупреждения — с кодом из единого реестра
  (`docs/Spec_Dispatcher.md`, раздел 11). Произвольные текстовые сообщения
  без кода запрещены.
- Хардкод путей, диапазонов и лимитов запрещён — использовать настройки
  (`GetProjectRoot`, `GetSettingLong`, `GetSettingText`, `LegendRange`,
  `MaxTypesPerTable`).
- Бинарные Excel-файлы (`*.xlsx`, `*.xlsm`, `*.docx`) в репозиторий не добавлять.
- Старые промты не удалять. Новый промт — отдельным файлом в `prompts/`.
- Не сломать сборку схемы: `Mod_Structure.BuildFlatStructure` /
  `WriteFlatTable` (7 колонок A–G, динамическая легенда из B8).
- Не менять базовую логику `ColorToType`, `LeadCode`, `CodeDepth`, `ParentName`,
  `CalcRowScore` без отдельного согласования.
- Не удалять проверки ссылочной целостности, уникальности и финальную валидацию.
- Не переносить реестр обратно в `Mod_Assembler`.
- Не включать проверки смарт-папок и отображения на диске как обязательные
  без требования спецификации.
- Не менять состав колонок плоской таблицы без фиксации в спецификации.
- Не переписывать модуль целиком — только пошаговая замена инфраструктуры.
- Новые глобальные переменные — только с описанным жизненным циклом.
- «Системное имя типа» кодом не генерировать — оставлено на ИИ.

## 5. VBA-соглашения (из практики проекта)

- `ListObject.HeaderRange` после `Resize` может давать ошибку 438. Читать
  заголовки через `Worksheet.Range("A1:H1")`.
- В циклах `For i = 1 To N` в обработчиках ошибок использовать именованные
  метки (`Resume NextNodeLog`), а не `Resume Next`.
- Строковые литералы с кавычками внутри экранировать (`""`). Перед коммитом
  проверять компиляцию (Debug → Compile).
- Результат `Split()` присваивать `Variant`, иначе ошибка компиляции.
- Все `Private Const` — до первой процедуры `Sub`/`Function` в модуле.
- Текстовые файлы (шаблоны `.md`, реестры `.txt`, готовые промты, `Шаги.txt`)
  читать и писать в UTF-8; при чтении — автоопределение (UTF-8 → Windows-1251).
  Ошибки записи — `P005`, ошибки/пустое чтение — `P006` (предупреждение).

## 6. Что читать перед задачей

- `docs/Spec_Dispatcher.md` — устройство Препроцессора, коды ошибок, правила
  промтов и реестров.
- `docs/Spec_Optimization.md` — таблица задач, порядок выполнения, тесты
  «После <ID>», раздел «Что НЕ делать».
- `docs/Project_Map.md` — состав модулей, карта промтов, поток данных,
  известные подводные камни.
- `docs/Journal.md` — последние записи: что уже сделано и какие решения приняты.
- `CONTRIBUTING.md` — ветки, PR, чек-лист ревью, работа с промтами.
- `docs/Handoff.md` — формы передачи A/B/B'/C/D/E.

## 7. Формат ответа кодера

- Код — скорректированные процедуры/фрагменты целиком с указанием
  «заменить процедуру X в файле Y» / «вставить после строки Z».
- Служебные файлы — блоки для `Spec_Optimization.md`, `Journal.md`,
  `Project_Map.md`, `prompts/CHANGELOG.md`.
- Текст коммита — заголовок + тело для `git commit -m`.
- Чек-лист переноса + самопроверка по критериям приёмки.
- Если работа идёт в резервном режиме (форма B'), шапка: `РЕЖИМ: B'-A | B'-R | B'-M`
  и 4 блока выхода (код, служебные файлы, текст коммита, чек-лист).

## 8. Чего не делать

- Не использовать GitHub Issues как точку постановки задач: постановка идёт
  через браузерный чат по форме B (Handoff.md).
- Не создавать PR и не делать push.
- Не сообщать SHA — это зона пользователя.
- Не запрашивать реальные `*.xlsx` / `*.docx` — их структура описана
  в `docs/Data_Schema.md` и `samples/`.
- Не менять `docs/Handoff.md`, `CONTRIBUTING.md`, `AGENTS.md` без отдельной
  задачи.
