# Техническое задание на оптимизацию для QWEN-Coder

Документ задаёт порядок оптимизации исходных модулей `Mod_Structure` и `Mod_Assembler` и создание недостающих модулей препроцессора.

## 2. Порядок выполнения

Порядок построен так, чтобы каждая следующая задача опиралась на уже созданную инфраструктуру и не ломала промежуточные состояния.

### Этап 1. Инфраструктура

Выполнить:

1. OPT-01
2. OPT-02
3. OPT-03
4. OPT-06

Обоснование:

- Сначала нужен единый служебный модуль, иначе каждый модуль продолжит создавать собственные журналы, пути и сообщения.
- Затем нужны папки проекта, чтобы было куда писать входные, выходные и служебные файлы.
- Затем нужна конфигурация, чтобы пути, режимы и правила не были зашиты в код.
- Затем нужен единый справочник ошибок, чтобы последующие изменения уже использовали правильные коды.

### Этап 2. Входной модуль

Выполнить:

1. OPT-04
2. OPT-05

Обоснование:

- `Mod_Structure` первым получает исходные данные. Если вход останется через диалог, дальнейшая автоматизация будет невозможна.
- После перевода входа на фиксированную папку нужно сразу подключить единый журнал, чтобы не закреплять старый способ логов.

### Этап 3. Очистка модуля сборки

Выполнить:

1. OPT-07
2. OPT-09
3. OPT-10
4. OPT-11
5. OPT-12

Обоснование:

- Сначала удаляются или изолируются проверки, которых нет в спецификации. Это уменьшает площадь изменений.
- Затем наводится порядок в словарях и глобальном состоянии.
- После этого крупная процедура разделяется на этапы.
- Затем корректируются потенциально опасные автоисправления и правила именования.

### Этап 4. Реестры

Выполнить:

1. OPT-08
2. OPT-13

Обоснование:

- Реестры должны строиться на уже очищенных и проверенных данных.
- Сначала `Mod_Assembler` готовится передавать данные, затем создаётся самостоятельный `Mod_Registry`.

### Этап 5. Новые пользовательские и служебные функции

Выполнить:

1. OPT-14
2. OPT-15
3. OPT-16
4. OPT-17
5. OPT-18

Обоснование:

- Промты имеют смысл только после появления реестров.
- Пользовательский интерфейс имеет смысл после стабильных внутренних запусков.
- Защита листов, документация и служебные действия относятся к завершающему слою и не должны блокировать основную логику.

### Этап 6. Контроль качества

Выполнить:

1. OPT-19

Обоснование:

- Проверочные сценарии должны фиксировать уже реализованное поведение и защищать его от регрессии.

## 3. Тесты после каждой задачи

Ниже описано, как проверить выполнение задач без запуска Excel. Проверка выполняется по изменению структуры кода, именам процедур, тексту сообщений, составу файлов и ожидаемому поведению.

### После OPT-01

- В проекте присутствует модуль `Mod_Util`.
- В нём есть процедуры для работы с путями, журналом и справочником ошибок.
- В коде нет прямых записей журнала в обход `Mod_Util`.
- У каждого сообщения есть код, категория и понятный текст.

### После OPT-02

- В проекте присутствует модуль `Mod_Folders`.
- Код содержит процедуру создания обязательных папок проекта.
- Поведение должно быть таким: если папка отсутствует, она создаётся; если папка уже есть, данные не удаляются.
- Ошибки доступа и отсутствия пути должны попадать в журнал.

### После OPT-03

- Конфигурация читается из фиксированной папки конфигурации.
- В коде нет жёстко зашитых пользовательских путей, кроме базового пути проекта.
- При отсутствии файла конфигурации формируется понятная ошибка.
- При повреждённой конфигурации формируется ошибка с кодом.

### После OPT-04

- В `Mod_Structure` больше нет вызова диалога выбора файла.
- Входной файл схемы читается из фиксированной папки `01_Схема`.
- При отсутствии входного файла формируется ошибка с кодом.
- Поведение должно быть одинаковым при каждом запуске.

### После OPT-05

- Все записи журнала проходят через `Mod_Util`.
- Трассируемость пишется через единый механизм.
- Файлы журнала и трассируемости имеют ожидаемые имена и расположение.
- Повторный запуск не создаёт неуправляемые копии файлов без правил именования.

### После OPT-06

- У каждой ошибки и каждого предупреждения есть единый код.
- Одна и та же ситуация в разных модулях получает один и тот же код.
- Отчёты об ошибках и предупреждениях могут быть прочитаны как список кодов и текстов.
- В коде нет произвольных текстовых сообщений без кода.

### После OPT-07

- Проверки, отсутствующие в спецификации, не выполняются по умолчанию.
- Если проверка оставлена как сервисная, она управляется через конфигурацию.
- Проверка смарт-папок и проверка отображения на диске не блокируют корректный прогон.
- Состав активных проверок можно объяснить требованиями спецификации.

### После OPT-08

- `Mod_Assembler` больше не отвечает за финальное построение реестра.
- Данные для реестра передаются в отдельный модуль или подготавливаются для него.
- В коде видна граница между проверкой данных и формированием реестра.
- Повторный запуск не создаёт два реестра разными механизмами.

### После OPT-09

- Словари инициализируются явно.
- Перед повторным запуском состояние очищается.
- Нет глобальных переменных, которые неявно используются несколькими процедурами без объявления источника.
- Поведение после двух последовательных запусков должно быть одинаковым.

### После OPT-10

- `ValidateAndAssemble` не является единственной процедурой, выполняющей все действия.
- Есть отдельные этапы: инициализация, проверка типов, проверка атрибутов, проверка иерархии, финальные проверки, отчёты.
- Каждый этап имеет понятное имя.
- Ошибка на одном этапе не мешает понять, какой этап завершился успешно.

### После OPT-11

- Автоисправление иерархии фиксируется в журнале.
- Изменения можно отличить от исходных данных.
- Есть режим или признак, который запрещает автоматическое исправление.
- Пользователь может понять, какие строки были исправлены.

### После OPT-12

- Правила CamelCase соответствуют спецификации.
- Разрешённые цифры не вызывают ложных ошибок.
- Запрещённые цифры фиксируются отдельным кодом.
- Сообщения об именовании одинаковы для типов и атрибутов, если природа ошибки одинакова.

### После OPT-13

- В проекте присутствует модуль `Mod_Registry`.
- Реестры формируются этим модулем.
- Реестры содержат ожидаемые наборы типов, атрибутов и связей.
- Изменение данных в `Mod_Assembler` не должно требовать ручной правки логики реестра.

### После OPT-14

- В проекте присутствует модуль `Mod_Prompt`.
- Промты формируются из данных реестров.
- Файлы промтов сохраняются в отдельной папке.
- Старые промты не удаляются, а новые создаются как новые файлы.

### После OPT-15

- В проекте присутствует модуль `Mod_UI`.
- Кнопки или меню вызывают правильные режимы.
- Мягкий и финальный режимы различаются.
- Пользовательский запуск не требует ручного выбора макроса из списка.

### После OPT-16

- Листы с результатами имеют ожидаемое оформление.
- Служебные листы защищены от случайного редактирования.
- Подсветка проблем соответствует типам ошибок.
- Защита не блокирует служебные процедуры обновления данных.

### После OPT-17

- Модуль `Mod_Docs` способен формировать README или служебную справку.
- Документация содержит актуальный состав модулей.
- В тексте документации нет ссылок на несуществующие модули.
- Повторная генерация не разрушает дополнения, если они должны сохраняться, либо явно перезаписывает автоматическую часть.

### После OPT-18

- Служебные операции открытия папок реализованы.
- Открытие папки журналов, папки результатов и папки промтов выполняется из единого механизма.
- Ошибка отсутствия папки пишется в журнал.
- Действия пользователя не требуют ручного поиска путей.

### После OPT-19

- Для каждого критичного сценария есть описание ожидаемого поведения.
- Есть сценарии для отсутствия входного файла, повреждённой конфигурации, ошибок уникальности, ошибок ссылок, ошибок иерархии.
- Есть сценарии для успешного прогона.
- Каждый сценарий можно проверить по коду, журналу и ожидаемым файлам.

## 4. Что НЕ делать

Чтобы не сломать работающую логику, запрещается:

1. Менять базовую логику `ColorToType`, если цветовая легенда уже согласована с бизнес-смыслом схемы.
2. Менять логику `LeadCode`, если она корректно реализует принятый формат кодов.
3. Менять логику `CodeDepth`, если она корректно вычисляет уровень вложенности.
4. Менять логику `ParentName` до полного понимания того, как определяется родитель в исходной схеме.
5. Удалять проверки ссылочной целостности типов и атрибутов.
6. Удалять проверки уникальности.
7. Удалять финальную валидацию перед формированием отчётов.
8. Упрощать отчёты об ошибках и предупреждениях до неструктурированного текста.
9. Переносить реестр в `Mod_Assembler` обратно после выноса в `Mod_Registry`.
10. Включать проверки смарт-папок и отображения на диске как обязательные без требования спецификации.
11. Менять состав колонок плоской таблицы без фиксации изменения в спецификации.
12. Менять формулу `CalcRowScore` без отдельного согласования.
13. Удалять старые файлы промтов при генерации новых версий.
14. Переписывать весь модуль целиком вместо пошаговой замены инфраструктуры.
15. Вводить новые глобальные переменные без необходимости и без описания их жизненного цикла.
