## 2. Порядок выполнения и правила приемки

### 2.1. Правила
1. **Правило побайтовой приёмки:** Статус «✅ Выполнено» присваивается **только** после побайтовой сверки `git show <SHA>` с пунктами ТЗ. Запрещено ставить «Выполнено» на основании словесных отчётов или предположений.
2. **Правило атомарности расширений:** Любое изменение расширения генерируемых файлов (например, `.md` → `.txt`) должно выполняться **в одном коммите** с модификацией парсера имён/счётчиков (`GetNextIterationNumber`), чтобы предотвратить сброс нумерации и потерю связи с историей итераций.
3. **Правило диагностики ошибок:** Во всех обработчиках `ErrHandler` переменные `Err.Number` и `Err.Description` должны сохраняться в локальные переменные **до** любых операций `On Error Resume Next` или очистки объектов (`Set obj = Nothing`). Это предотвращает появление пустых сообщений об ошибках в логах.
4. **Правило работы с итераторами `Dir()`:** Категорически запрещено использование stateful-функции `Dir()` во вложенных циклах или процедурах, вызывающих файловые операции. Использовать только безопасную обёртку `GetFileListArray` + цикл `For`.
5. **Правило симметричной архивации:** Архивация артефактов (промт + ответ ИИ + входной CSV-фрагмент) должна выполняться в рамках одного логического блока разбора, обеспечивая целостность истории итераций и чистоту рабочей папки `05_Фрагменты шагов`.

## 3. Что не делать
*(Анти-паттерны, выявленные в ходе проекта)*

- ❌ Не использовать `Dir()` для проверки существования файлов в циклах (сбрасывает итератор).
- ❌ Не позволять ИИ размазывать типы одного паттерна по разным строкам/шагам.
- ❌ Не генерировать промты с пустой таблицей CSV (должна быть проверка `csvRows = 0`).
- ❌ Не игнорировать `Err.Description` перед вызовом `Err.Clear`.
- ❌ Не менять базовую логику `ColorToType`, если цветовая легенда уже согласована с бизнес-смыслом схемы.
- ❌ Не менять логику `LeadCode`, если она корректно реализует принятый формат кодов.
- ❌ Не менять логику `CodeDepth`, если она корректно вычисляет уровень вложенности.
- ❌ Не менять логику `ParentName` до полного понимания того, как определяется родитель в исходной схеме.
- ❌ Не удалять проверки ссылочной целостности типов и атрибутов.
- ❌ Не удалять проверки уникальности.
- ❌ Не удалять финальную валидацию перед формированием отчётов.
- ❌ Не упрощать отчёты об ошибках и предупреждениях до неструктурированного текста.
- ❌ Не переносить реестр в `Mod_Assembler` обратно после выноса в `Mod_Registry`.
- ❌ Не включать проверки смарт-папок и отображения на диске как обязательные без требования спецификации.
- ❌ Не менять состав колонок плоской таблицы без фиксации изменения в спецификации.
- ❌ Не менять формулу `CalcRowScore` без отдельного согласования.
- ❌ Не удалять старые файлы промтов при генерации новых версий.
- ❌ Не переписывать весь модуль целиком вместо пошаговой замены инфраструктуры.
- ❌ Не вводить новые глобальные переменные без необходимости и без описания их жизненного цикла.
- ❌ Не генерировать «Системное имя типа» кодом — оставлено на ИИ (ответ 6.3).
- ❌ Не переносить №0.1/№0.2 на Python в рамках текущего этапа — только PRE-01…PRE-05 (backlog `W-MIGRATE-STEP01-TO-PYTHON`).
- ❌ Не удалять столбец «Паттерн» из плоской таблицы после PRE-04.

#### После OPT-01
- В проекте присутствует модуль `Mod_Util`.
- В нём есть процедуры для работы с путями, журналом и справочником ошибок.
- В коде нет прямых записей журнала в обход `Mod_Util`.
- У каждого сообщения есть код, категория и понятный текст.

#### После OPT-02
- В проекте присутствует модуль `Mod_Folders`.
- Код содержит процедуру создания обязательных папок проекта.
- Поведение должно быть таким: если папка отсутствует, она создаётся; если папка уже есть, данные не удаляются.
- Ошибки доступа и отсутствия пути должны попадать в журнал.

#### После OPT-03
- Конфигурация читается из фиксированной папки конфигурации.
- В коде нет жёстко зашитых пользовательских путей, кроме базового пути проекта.
- При отсутствии файла конфигурации формируется понятная ошибка.
- При повреждённой конфигурации формируется ошибка с кодом.

#### После OPT-04
- В `Mod_Structure` больше нет вызова диалога выбора файла.
- Входной файл схемы читается из фиксированной папки `01_Схема`.
- При отсутствии входного файла формируется ошибка с кодом.
- Поведение должно быть одинаковым при каждом запуске.

#### После OPT-05
- Все записи журнала проходят через `Mod_Util`.
- Трассируемость пишется через единый механизм.
- Файлы журнала и трассируемости имеют ожидаемые имена и расположение.
- Повторный запуск не создаёт неуправляемые копии файлов без правил именования.

#### После OPT-06
- У каждой ошибки и каждого предупреждения есть единый код.
- Одна и та же ситуация в разных модулях получает один и тот же код.
- Отчёты об ошибках и предупреждениях могут быть прочитаны как список кодов и текстов.
- В коде нет произвольных текстовых сообщений без кода.

#### После OPT-07
- Проверки, отсутствующие в спецификации, не выполняются по умолчанию.
- Если проверка оставлена как сервисная, она управляется через конфигурацию.
- Проверка смарт-папок и проверка отображения на диске не блокируют корректный прогон.
- Состав активных проверок можно объяснить требованиями спецификации.

#### После OPT-08
- `Mod_Assembler` больше не отвечает за финальное построение реестра.
- Данные для реестра передаются в отдельный модуль или подготавливаются для него.
- В коде видна граница между проверкой данных и формированием реестра.
- Повторный запуск не создаёт два реестра разными механизмами.

#### После OPT-09
- Словари инициализируются явно.
- Перед повторным запуском состояние очищается.
- Нет глобальных переменных, которые неявно используются несколькими процедурами без объявления источника.
- Поведение после двух последовательных запусков должно быть одинаковым.

#### После OPT-10
- `ValidateAndAssemble` не является единственной процедурой, выполняющей все действия.
- Есть отдельные этапы: инициализация, проверка типов, проверка атрибутов, проверка иерархии, финальные проверки, отчёты.
- Каждый этап имеет понятное имя.
- Ошибка на одном этапе не мешает понять, какой этап завершился успешно.

#### После OPT-11
- Автоисправление иерархии фиксируется в журнале.
- Изменения можно отличить от исходных данных.
- Есть режим или признак, который запрещает автоматическое исправление.
- Пользователь может понять, какие строки были исправлены.

#### После OPT-12

- Разрешённые цифры не вызывают ложных ошибок.
- Запрещённые цифры фиксируются отдельным кодом.
- Сообщения об именовании одинаковы для типов и атрибутов, если природа ошибки одинакова.

#### После OPT-13
