# Шаблоны передачи между участниками

Цель: исключить искажения при передаче информации владелец ↔ DeepSeek ↔ QWEN-Coder ↔ ревьюер. Передаём не пересказ своими словами, а файлы и готовые блоки.

## A. Владелец → DeepSeek (постановка / корректировка задачи)

```text
РОЛЬ: оркестратор проекта pilot-db-preprocessor. Правила работы: CONTRIBUTING.md.
КОНТЕКСТ: Spec_Optimization.md, раздел 1 — таблица задач со статусами (вставить).
ЖУРНАЛ: последние 2 записи из docs/Journal.md (вставить).
ЗАДАЧА: <OPT-xx / W<n>, название>.
ВОПРОС: <один конкретный вопрос>.
ФОРМАТ ОТВЕТА: текст задачи для QWEN-Coder (по форме B) + критерии приёмки.
```

## B. DeepSeek → QWEN-Coder (текст задачи)

```text
ЗАДАЧА: OPT-xx — <название из Spec_Optimization.md>.
СВЯЗАННЫЕ ФАЙЛЫ: <Mod_*.bas, docs/...>.
ЧТО СДЕЛАТЬ: <пункты по чек-листу, без «и т.д.» и без «...»>.
ОГРАНИЧЕНИЯ: трогать только файлы <перечень>; журналирование через Mod_Util;
коды ошибок по единому реестру; бинарные Excel-файлы не добавлять;
старые промты не удалять.
КРИТЕРИИ ПРИЁМКИ: тесты из Spec_Optimization.md «После OPT-xx»: <перечислить>.
Ветка и PR — по настройкам QWEN-Coder (for-coder / автопрефикс [<ID>]).
ОБЯЗАТЕЛЬНО В ТОМ ЖЕ PR (Definition of Done):
1. Spec_Optimization.md — колонка «Статус»: <ID задачи> → «Выполнено».
2. docs/Journal.md — запись: дата, <ID задачи>, что сделано (1–3 строки),
   SHA коммита — оставить прочерк «SHA: ___ (заполняет пользователь
   после создания PR)». Кодер Journal пишет, SHA не подставляет.
3. docs/Project_Map.md — обновить, если менялась архитектура/состав
   модулей/карта промтов; если не менялась — строкой «Project_Map.md
   не менялся: архитектура без изменений».
4. prompts/CHANGELOG.md — запись, если менялись prompts/*.md; если
   не менялись — строкой «CHANGELOG не менялся: промты не затрагивались».
5. В описании PR — перечислить изменённые файлы и критерии приёмки,
   которые выполнены (по одному пункту на критерий).
6. Сообщить в чат оркестратора: «<ID> готов к PR». PR и SHA сообщает
   пользователь отдельным сообщением после создания PR вручную.

Правило: если хотя бы один из пп. 1–4 не выполнен — PR не принимается
(возврат на доработку), даже если код корректен.
```

## C. DeepSeek → ревьюер

Оформление PR — по `CONTRIBUTING.md` (код задачи, список изменений, список проверок).

```text
PR: {{PR_URL}}            ← заполняется по данным от пользователя (кодер PR не создаёт)
КОММИТ: {{COMMIT_SHA}}    ← заполняется по данным от пользователя (кодер SHA не сообщает)
ЗАДАЧА: {{TASK_ID}}

Примечание: поля PR и КОММИТ заполняет пользователь после создания PR
вручную. Кодер PR не создаёт и SHA в чат не сообщает — это делает
пользователь.
```

СПИСОК ПРОВЕРОК (по критериям приёмки из Spec_Optimization.md «После <ID>»):
1. <пункт 1>
2. <пункт 2>
...

ОСОБОЕ ВНИМАНИЕ:
- Сборка схемы (Mod_Structure.BuildFlatStructure / WriteFlatTable) — не сломана.
- Чужие модули не затронуты (только перечисленные в задаче).
- Журналирование — через Mod_Util (WriteLog / WriteError / WriteWarning).
- Хардкод путей, диапазонов, лимитов — отсутствует (используются настройки).

ФОРМАТ ОТВЕТА: по форме D.

При необходимости приложить текстовую версию изменений — к адресу PR
добавляется `.diff` или `.patch`:

```text
https://github.com/Dronyc/pilot-db-preprocessor/pull/<N>.diff
```

## D. Ревьюер → заключение (владельцу и DeepSeek)

```text
PR #[N] — [W<n>] <название>. Задача: OPT-xx.
ЧЕК-ЛИСТ (CONTRIBUTING.md): по пунктам — ок / замечание.
НАЙДЕНО: список замечаний с указанием файлов и строк.
ВЕРДИКТ: одобрить / вернуть на доработку.
```

## E. Владелец → Z.ai / GLM (независимый арбитраж)

```text
РОЛЬ: независимый ревьюер и арбитр. Репозиторий публичный:
https://github.com/Dronyc/pilot-db-preprocessor — ревьюер сам скачает код и diff.
ВОПРОС: PR #[N] / конфликт QWEN и DeepSeek / спорное архитектурное решение.
СУТЬ СПОРА: <1–2 предложения>.
```

## Правила работы и контроль контекста

- Форма C — DeepSeek → ревьюер (не QWEN-Coder → ревьюер). Ревьюер правок не вносит, только отчёт по форме D.
