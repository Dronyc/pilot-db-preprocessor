# Шаблоны передачи между участниками

Цель: исключить искажения при передаче информации владелец ↔ DeepSeek ↔ QWEN-Coder ↔ ревьюер. Передаём не пересказ своими словами, а файлы и готовые блоки.

## A. Владелец → DeepSeek (постановка / корректировка задачи)

```text
РОЛЬ: оркестратор проекта pilot-db-preprocessor. Правила работы: CONTRIBUTING.md.
КОНТЕКСТ: Spec_Optimization.md, раздел 1 — таблица задач со статусами (вставить).
ПОСТОЯННЫЕ ПРАВИЛА: AGENTS.md (корень репозитория).
ЖУРНАЛ: последние 2 записи из docs/Journal.md (вставить).
ЗАДАЧА: <OPT-xx / W<n>, название>.
ВОПРОС: <один конкретный вопрос>.
ФОРМАТ ОТВЕТА: текст задачи для QWEN-Coder (по форме B) + критерии приёмки.
```

## B. DeepSeek → QWEN-Coder (текст задачи)

Постоянные правила — в `AGENTS.md` (корень репозитория). Форма B их не дублирует.

```text
ЗАДАЧА: OPT-xx — <название из Spec_Optimization.md> (W<N>).
СВЯЗАННЫЕ ФАЙЛЫ: <Mod_*.bas, docs/...>.
ЧТО СДЕЛАТЬ:
1. <конкретное действие>
2. <конкретное действие>
КРИТЕРИИ ПРИЁМКИ (Spec_Optimization.md, «После OPT-xx»):
1. <критерий 1>
2. <критерий 2>
```

## B'. DeepSeek → исполнительный чат (резервный режим)

Форма B' применяется, когда основная схема (кодер QWEN, формы B/C/D)
недоступна. Исполнительный чат получает задание и возвращает 4 блока.
Переключение схем — по решению владельца, с фиксацией в Journal.md.
Существующие формы B, C, D при этом сохраняются и не отменяются.

Шапка формы: «РЕЖИМ: B'-A | B'-R | B'-M».

### Под-схемы

- **B'-A (attached)** — работа только с файлами, приложенными к сообщению.
  В репозиторий не ходит.
- **B'-R (read-only repo)** — репозиторий на чтение:
  https://github.com/Dronyc/pilot-db-preprocessor (public).
  Только чтение; push/PR запрещены.
- **B'-M (mixed)** — приложенные файлы + репозиторий на чтение.
  Правило приоритета:
  1) приложенные файлы — первичный источник для правки;
  2) репозиторий — вспомогательный (контекст, вызовы, реестр кодов,
     структура листа); сверка приложенного с актуальным состоянием
     for-coder;
  3) если приложенного файла нет, а в репозитории есть — можно прочитать
     и править с пометкой в БЛОКЕ 4 «файл X взят из репозитория
     (ветка/коммит Y), не приложен»;
  4) если файл есть и в приложении, и в репозитории, и они различаются —
     приоритет у приложенного; расхождение фиксируется в БЛОКЕ 4
     (решает пользователь);
  5) push/PR — запрещены (зона пользователя).

### Выход исполнительного чата — 4 блока

**БЛОК 1. Код** — скорректированные процедуры/фрагменты целиком +
указание «заменить процедуру X в файле Y» / «вставить после строки Z».

**БЛОК 2. Служебные файлы** — Spec_Optimization.md (статус),
Journal.md (запись, SHA — прочерк «заполняет пользователь»),
Project_Map.md (строка), prompts/CHANGELOG.md (если промты).

**БЛОК 3. Текст коммита** — заголовок + тело для `git commit -m`.

**БЛОК 4. Чек-лист переноса + самопроверка** — файл → действие
(append/заменить/вставить) → проверка после правки; самопроверка по
критериям приёмки; расхождения (для B'-M) — отдельным пунктом.

## C. DeepSeek → ревьюер

Постоянные правила проверки — в `AGENTS.md` (раздел 4). Форма C их не дублирует.

```text
PR: {{PR_URL}}
КОММИТ: {{COMMIT_SHA}}
ЗАДАЧА: {{TASK_ID}}

СПИСОК ПРОВЕРОК (по критериям приёмки из Spec_Optimization.md «После <ID>»):
1. <пункт 1>
2. <пункт 2>
...

ФОРМАТ ОТВЕТА: по форме D.

При необходимости приложить текстовую версию изменений — к адресу PR
добавляется .diff или .patch:
https://github.com/Dronyc/pilot-db-preprocessor/pull/<N>.diff
```

## D. Ревьюер → заключение (владельцу и DeepSeek)

```text
PR #[N] — [W<n>] <название>. Задача: OPT-xx.
ЧЕК-ЛИСТ (CONTRIBUTING.md): по пунктам — ок / замечание.
НАЙДЕНО: список замечаний с указанием файлов и строк.
ВЕРДИКТ: одобрить / вернуть на доработку.
```

## E. Владелец → Z.ai / GLM (независимый арбитраж)

```text
РОЛЬ: независимый ревьюер и арбитр. Репозиторий публичный:
https://github.com/Dronyc/pilot-db-preprocessor — ревьюер сам скачает код и diff.
ВОПРОС: PR #[N] / конфликт QWEN и DeepSeek / спорное архитектурное решение.
СУТЬ СПОРА: <1–2 предложения>.
```

## Правила работы и контроль контекста

- Форма C — DeepSeek → ревьюер (не QWEN-Coder → ревьюер). Ревьюер правок не вносит, только отчёт по форме D.

### Схемы работы

- Основная схема: кодер QWEN, формы B (DeepSeek → QWEN-Coder), C
  (DeepSeek → ревьюер), D (ревьюер → заключение).
- Резервная схема: исполнительные чаты, форма B' с под-схемами
  B'-A / B'-R / B'-M.
- Переключение схем — по решению владельца, с фиксацией в Journal.md.

### Зоны ответственности

- PR/SHA — зона пользователя. Кодер/исполнительный чат PR не создают,
  push не делают, SHA не сообщают.
- Journal — кодер/исполнительный чат; SHA — прочерк
  «заполняет пользователь».
